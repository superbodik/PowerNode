Authentication

Every request under /api/v1 needs an Authorization: Bearer <token> header. There are two kinds of token.

API keys — what you want for automation

Create one from Account → API Keys in the panel (this first step needs a browser — there's no way to mint a key without already being logged in). Pick exactly the permissions the key needs; leave all boxes unchecked for a key with the same access as your account, or check specific ones to scope it down. The raw token is shown once, at creation — the panel only ever stores its hash, so copy it immediately.

curl -H "Authorization: Bearer pk_live_xxxxxxxxxxxx" \
  https://your-panel.example.com/api/v1/servers

API keys never expire on their own and aren't tied to a browser session — delete them from the same page when a key is no longer needed.

Permission codes

These are the exact strings a key (or a subuser, on the sharing side) can be granted. Anything not granted gets 403 Forbidden, not a partial response.

CodeGrants
servers.readList and view servers
servers.writeCreate and delete servers
control.startPower on
control.stopPower off
control.restartRestart
control.killForce-kill
consoleConsole WebSocket (read + send commands)
files.read / files.writeBrowse/download vs. edit/upload/delete files
databases.read / databases.writeView vs. create/delete per-server databases
domains.read / domains.writeView vs. attach/remove custom domains
backups.read / backups.writeView/download vs. create/restore/delete backups
schedules.read / schedules.writeView vs. create/toggle/delete cron schedules
allocations.read / allocations.writeView vs. add/remove a server's own ports

The server owner and admins always have full access regardless of key scope — these codes only ever restrict a key or a subuser, never grant more than the account already has.

JWT (what the browser uses)

The panel's own frontend logs in via POST /auth/login (email + password, + TOTP code if 2FA is on) and refreshes via POST /auth/refresh. You can use this flow too, but for scripts and CI a long-lived API key is almost always simpler — no refresh logic to write, and you can scope it down instead of holding a full-account session.

Base URL
Every path on this page is relative to https://<your-panel>/api/v1. Only /auth/login, /auth/refresh and the two-factor endpoints on login are rate-limited; the rest of the API has no built-in throttling — be a reasonable neighbor to your own panel.

Automating server provisioning

Everything the "Create Server" form does is five plain requests. This is the whole thing, start to finish.

Server creation is synchronous — the panel calls the node's daemon inline and only returns 201 once the container actually exists. There's no job queue to poll: a successful response means the server is real and ready for a power call.

export PANEL="https://your-panel.example.com"
export TOKEN="pk_live_xxxxxxxxxxxx"   # from Account → API Keys
GET /nodes any authenticated user

Pick a node to deploy on. Non-admins only see nodes marked public.

curl -s -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/nodes" | jq '.[] | {id, name, is_public}'
GET /allocations?node_id={id}&free=true any authenticated user

Find a free port on that node to bind the new server to. Non-admins can only query allocations on nodes marked public — same visibility rule as picking a node above.

curl -s -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/allocations?node_id=1&free=true" | jq '.[0]'
GET /eggs any authenticated user

List available deploy templates — Minecraft, a generic Python app, the static-HTML egg, your own Docker image, and so on — including each egg's editable environment variables.

curl -s -H "Authorization: Bearer $TOKEN" \
  "$PANEL/api/v1/eggs" | jq '.[] | {id, name, docker_image}'
POST /servers servers.write

Create it. allocation_id is optional — a server can also be created with no port and have one added afterward via the network endpoints below.

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "name": "mc-survival-01",
    "node_id": 1,
    "egg_id": 2,
    "docker_image": "itzg/minecraft-server",
    "startup_command": "",
    "environment": { "EULA": "TRUE" },
    "memory_mb": 2048,
    "swap_mb": 0,
    "disk_mb": 10240,
    "allocation_id": 42
  }' \
  "$PANEL/api/v1/servers"
# -> 201 {"id": 17, "uuid": "6f1c...-...-..."}
POST /servers/{uuid}/power control.start

Turn it on.

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"action": "start"}' \
  "$PANEL/api/v1/servers/6f1c.../power"
One key, every step
A single API key with servers.read, servers.write and control.start covers this whole flow — mint it once from Account → API Keys and the rest is headless from there. Wrap the five calls above in whatever provisions your fleet: a CI job, a Discord bot's /deploy command, a signup webhook — the panel doesn't care who's calling.

Servers

GET/serversservers.read

List every server you own, share access to, or (as admin) every server on the panel.

GET/servers/{uuid}servers.read

Full detail for one server — status, resource limits, primary address, node, egg.

POST/serversservers.write

See Automating server provisioning above for the full request body.

DELETE/servers/{uuid}servers.write

Stops and removes the container plus all its data. Admins can add ?force=true to delete the panel record even if the node is unreachable.

POST/servers/{uuid}/suspend / /unsuspendadmin

Suspend stops the server and blocks starting it again until unsuspended — for billing holds or abuse response, not a regular power action.

Power actions

POST /servers/{uuid}/power control.*

Body: {"action": "start" | "stop" | "restart" | "kill"}. Each action needs its own matching permission (control.start for start, etc.) — a key scoped to only control.stop can't also kill. Actions are idempotent: calling start on an already-running server, or kill on an already-dead one, succeeds rather than erroring.

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{"action": "restart"}' \
  "$PANEL/api/v1/servers/{uuid}/power"
# -> 200 {"server_uuid": "...", "success": true, "state": "starting"}

Live state and resource usage (CPU/RAM/disk, updated every couple of seconds) are only available over the /ws/servers/{uuid} WebSocket, which the panel's own dashboard uses — there's no polling REST endpoint for it. Send the access token as the Sec-WebSocket-Protocol value to authenticate.

API keys don't work here
The WebSocket endpoints only accept a JWT access token from /auth/login — not an API key. A script that only needs REST (provisioning, power, files, …) never needs this; one that wants live stats or the console feed has to log in like the browser does.

Network (a server's own ports)

GET/servers/{uuid}/allocationsallocations.read

Every port published for this server. The oldest one is flagged is_primary — that's the address shown on the server card and what domains proxy to by default.

POST/servers/{uuid}/allocationsallocations.write

Body: {"port": 25566, "alias": "query port"} (alias optional). Port must be 1024–65535 and not one the node itself needs (22, 80, 443, 2022, or the node's own daemon port). Applying this recreates the server's container — files are kept, but it briefly restarts.

DELETE/servers/{uuid}/allocations/{id}allocations.write

Also recreates the container. Refused if it's the primary port and the server still has domains pointed at it — remove those first.

Domains

GET/servers/{uuid}/domainsdomains.read
POST/servers/{uuid}/domainsdomains.write

Body: {"domain": "sub.example.com", "email": "you@example.com", "allocation_id": 42} — email and allocation_id are both optional (email is used for Let's Encrypt renewal notices; omitting allocation_id uses the server's primary port). Point the domain's DNS A record at the node before calling this — certificate issuance needs it to already resolve. Subdomains work the same as root domains; each one can point at a different port to run several services off one server.

DELETE/servers/{uuid}/domains/{id}domains.write

Files

EndpointPermissionNotes
GET /servers/{uuid}/files?path=files.readList a directory
GET /servers/{uuid}/files/contents?path=files.readRead a file; response carries an X-File-Mtime header
PUT /servers/{uuid}/files/contents?path=files.writeWrite a file. Send X-Expected-Mtime (from the header above) to get a 409 instead of clobbering a concurrent edit
DELETE /servers/{uuid}/files?path=files.writeDelete a file or directory
POST /servers/{uuid}/files/directory?path=files.writeCreate a directory
POST /servers/{uuid}/files/renamefiles.writeBody: {"from": "...", "to": "..."}

All paths are jailed to the server's own /home/container — there's no way to escape it with .. segments.

Schedules

POST/servers/{uuid}/schedulesschedules.write

A schedule is a cron trigger plus an ordered list of steps, each with its own delay before it runs:

curl -s -X POST -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
  -d '{
    "name": "Nightly restart",
    "cron_minute": "0", "cron_hour": "4",
    "cron_day_of_week": "*", "cron_day_of_month": "*",
    "only_when_online": true,
    "tasks": [
      { "action": "power", "payload": "stop", "time_offset_seconds": 0 },
      { "action": "backup", "payload": "nightly", "time_offset_seconds": 5 },
      { "action": "power", "payload": "start", "time_offset_seconds": 30 }
    ]
  }' \
  "$PANEL/api/v1/servers/{uuid}/schedules"

action is one of power (payload: start/stop/restart/kill), command (payload: a console command string), or backup (payload: a name, or blank to auto-name it). Cron fields use * or a literal number, no ranges or steps.

EndpointPermission
GET /servers/{uuid}/schedulesschedules.read
POST /servers/{uuid}/schedules/{id}/toggleschedules.write
DELETE /servers/{uuid}/schedules/{id}schedules.write

Errors

Plain HTTP status codes, plain-text body — no envelope, no error-code taxonomy to parse:

HTTP/1.1 403 Forbidden
Content-Type: text/plain; charset=utf-8

forbidden
StatusMeans
400Bad request body or query param
401Missing or invalid token
403Valid token, missing permission
404No such server/resource, or you can't see it
409Conflict — a port already in use, a file changed since you read it, a name collision
502The panel reached the node, but the node (or its daemon) rejected or failed the call

Not sure what a specific response means beyond this table? Check journalctl -u panel -f on the panel's server while you retry the call — see the Docs & Guides page for the full command reference.
